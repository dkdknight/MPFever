MPFever - Changelog
===================

0.3.13-experimental - the main menu no longer crashes when MPFever's menu file fails to load; electrified rail stations
  - FIX (issue #46): a rail station with electrified tracks built by another player was refused on the other games
    ("Construction Not Possible" in every form, then a resynchronisation). Its tracks use simple_catenary.street_template,
    which the replay did not recognise as the station's own tracks (only simple.street_template), so the station did not
    take the exact native construction replay. Checked: the station of the issue's log (modular cargo station, 2 tracks,
    catenary, 48 segments) replayed at 6 places of a large savegame: built 5 times with its 48 segments, refused once
    for a real collision with a road.
  - AUTOTEST: a game that crashed during the test (process closed, or no clock for 120 s: a crashed game can stay open
    after writing its crash save) now ends the test as "FAILED (a game closed)" instead of "IN SYNC". replayfile: an act
    with shift = {x, y} is moved there (at the height of the ground) to replay a player's build on another savegame.
  - NOTE (not MPFever): bulldozing a dead-end street with the engine's own removal proposal from a script can crash the
    game (assertion AreAllNodesEmpty in TransportNetworkSystem.cpp:635), also with MPFever not active. Seen on a large
    savegame from mod.io (Leawood); reported here so that crashes with that assertion are not taken for MPFever's.
  - FIX: when mpfever_menu.lua (or mpfever_pause.lua) failed to load, the game crashed at start with "module
    'mpfever_1::/gui/main/react.lua' not found". The game's require (base/init.lua) puts the file's path on its
    require stack before loading it and only takes it off when the file ran to its end: our failed file stayed on it,
    and the game's own "::/gui/..." files were then looked for in MPFever's folder. The line put in front of the menu
    now restores that stack when our file fails: the game starts, without the Multiplayer button, and the error is
    printed as [MPFEVER-MENU] in stdout.txt. Reproduced with a menu file that throws (before: 2 Lua errors, game
    stopped; now: main menu ready).

0.3.12-experimental - dedicated server (separate archive), pull requests #43 and #44 (Steelworm), #23 (SlikerDev)
  - FIX (PR #43): a released build counted as refused 150 frames after its release, even while the simulation half was
    still capturing it. A street through a town takes seconds to capture (1.7 s, 28 town buildings): it was given up,
    the other games stopped holding for it and built it a step late, with other houses taken away (desync). It now counts
    as refused after 150 frames and 4 handshakes with the simulation (900 frames in any case), and never while a capture
    waits to be shipped. Test switch MPFEVER_SLOWCAPTURE=<seconds>. Checked: captures made 3 s slower at 1x, 4x and in a
    pause, no build given up or late, in sync (before: 3 of 3 builds given up and built 4 steps late).
  - EXPERIMENTAL (PR #44, off by default, MPFEVER_BUILDLEAD=1 on every game): the builder leads. The builds of the
    street, track, station and stop tools and of the bulldozer are applied at once on the builder's game while the
    others stay behind it and replay them at the same step: from sending a road to the engine's answer 19 to 37 frames
    instead of 100 to 250. Only at 1x: above it, streets through a town released at once let the town development drift
    (houses placed differently with identical builds, 4 of 5 long runs at 2x and 4x); there the builds are held as usual.
    New autotest scenarios buildlead, towncross, dozenew.
  - NEW (PR #23, SlikerDev): dedicated server, MPFever.exe --server (or start-server.bat, in the separate archive
    MPFever-<version>-server.zip): the game of a PC of its own loads one world and hosts it, nobody plays on it, and
    the players join it as they join a host. The world no longer depends on the PC of one of the players. See SERVER.txt.
    - Settings in mpfever_server.properties next to MPFever.exe, written with their default values at the first start:
      world (the savegame), port, password, players at most, company mode, owner of the savegame's company, start
      money and speed, autosave, backups, restart after a crash, watchdog, message of the day.
    - As in Satisfactory and Factorio, the world pauses while nobody is connected and resumes when a player is in.
    - Autosave under the world's name (every 10 minutes by default; the world stops a few seconds), before a restart
      and when the server stops; a copy of each save in server\backups (the last 10 kept).
    - The game is started again when it closes, crashes, freezes (no sign of life for 180 s) or does not load the
      world, at most 3 times in 15 minutes. The players' MPFever reconnects by itself and receives the world again.
    - A console under the log of the server window: help, status, say, save, pause, resume, speed, kick, resync,
      restart, stop. Closing the window stops the server properly (the world is saved first).
    - A player whose game is not in the server's world yet (it reconnected after a restart of the server, still in
      its old world) only counts once its game has loaded the server's world.
  - NEW: joining a dedicated server: a "Password" field in the MPFever window of the main menu. A player is told why
    the server refused it (wrong password, server full, other MPFever version, kicked, server stopped) in the
    MPFever window and in the chat, and its MPFever does not try to reconnect. A connection that was not let in
    receives nothing of the session.
  - NEW (separate companies): a dedicated server plays no company. The savegame's own company goes to the player named
    by owner= in its settings, else to nobody.
  - NEW: the in-game MPFever window names the dedicated server above the players.
  - FIX: the main game script stays below Lua's limit of 200 locals with the server's additions (the script did not
    load at all: no session could start).

0.3.10-experimental - faster builds, vehicles bought together, purchases and line assignments in a pause
  - FIX (issue #34): a build appeared about 3 s after the click, and the game stopped at the click and reached the build's
    time in three stopped rounds. Two stop margins were stacked (the hold aimed a few steps before the build's time, and
    the stop zone added as many again), and the barrier, narrower than that margin, left a third round for the last
    step. The hold now aims at the build's time itself when exact steps are available (the stop zone already stops the
    game early enough and steps exactly from there), and exact steps towards a hold may go up to the step before the
    other game's next action could be stamped (its stamp distance), since they never overshoot. Measured with held
    builds in autotests: one stopped round per build instead of three; click to release 197 -> 142 frames (median) at
    1x, 210 -> 115 at 4x; every build still landed at its time on both games.
  - FIX (issue #34): a vehicle purchase that waited for the one before it (one purchase per step) was logged as a late
    action and locked the shorter stamp distance for the rest of the session. It is no longer counted as late.
  - FIX (issue #35, desync): vehicles bought together (same step) were created one per call of the simulation script,
    not one per step. That script also runs while the game time stands still (at a held build, at the barrier, behind a
    terrain tool), so a game standing still created several of them at one step that a running game created a step
    apart: other entity ids, the games drifted apart and reloaded. The step of the last purchase is now kept in the
    state saved with the game: one purchase per step on every game, also after a reload. The purchase watch counts game
    steps too. Reproduced with an autotest (four purchases at once and a held build): before, the fourth vehicle was
    created at different steps with different ids; now at the same steps with the same ids.
  - FIX (issue #36, desync): in a pause, vehicles bought and assigned to a line at once (the depot window assigns each one
    as soon as its purchase is confirmed): the assignment reached the other game before its purchase was registered
    there (only the engine's answer, a frame later, registers it), so it was skipped and every game reloaded. In a
    pause, after an action that creates a vehicle or a line, the following actions now wait for its answer (at most 600
    frames), in their order. Reproduced with an autotest in a pause: before, the assignments were skipped on the other
    game and the games desynced; now every assignment is applied everywhere.
  - TESTS: autotest scenarios buymany (four purchases at once, MPFEVER_BUYBUILD=1 with a held build) and buyline (purchases
    then line assignments, for a paused session); MPFEVER_OLDHOLDS=1, MPFEVER_OLDBUY=1 and MPFEVER_OLDPAUSED=1 bring back
    the previous behaviours for comparisons; the autotest builds log their hold frame.

0.3.9-experimental - track builds replayed with the tool's replacement maps, street upgrades in towns, PR #33
  - FIX (desync): a track or road build that joins an existing one, reshapes a curve or moves a junction node made the
    simulation drift apart a few minutes later (the reloads of our tests while building railways and adding trains). The
    builder's tool tells the engine which new segments and nodes replace which old ones; the engine then charges nothing
    for the replaced parts and keeps what was on them. The other games rebuilt the build without that information: they
    paid for the replaced parts again (the money differed after every such build) and the engine handled them as new
    ones, so every game numbered its next entities (vehicles, people...) differently, and the towns and the vehicles
    drifted apart. The capture now ships these maps, and a build that has them is replayed as a native proposal that
    carries them, with the tool's own build settings. Reproduced and checked with an autotest that moves a junction
    node: without the maps the costs and the entity numbering differed at once and the games desynced; with them the
    costs, the entity numbering and the state are identical.
  - FIX (desync): a street upgraded in a town, where the game moves town buildings for the wider street, left the other
    games with two town buildings fewer, and the towns drifted apart. The moved buildings were rebuilt as plain
    constructions, which are no town buildings (and the map of which old building each new one replaces is numbered from
    0 in the native proposal, from 1 in the script one). Such a build is now sent without the buildings: every game's
    engine takes the same buildings away and puts the same ones back (the game's random numbers are the same on every
    game). Checked with the upgrade autotest on a town street with 7 buildings: identical costs, ids and state.
  - MERGED PR #33 (SlikerDev): the IPv6 note of a failed connection comes after the other errors (#31); every host game
    a player receives gets a number of its own, also when the game is already running, and the parts of a host game half
    received are cleared when the connection drops (#29).
  - DIAGNOSTICS: every game logs the entity ids it gives to the segments and nodes of each build ("build ids t=..."):
    the same build must give the same ids on every game. The capture logs the replacement maps it ships ("maps ...").
  - TESTS: new autotest scenarios that build like the native tools (held and shipped as native builds): dsplit (a road
    cutting a segment), dsplitbusy (the same on a segment a vehicle is on), dnodemove (a junction node moved, with
    MPFEVER_SPLITMAPS=1 the tool's maps), dsignal (a signal on a track). Line waypoints checked on a train line (#27).

0.3.8-experimental - lobby, speed buttons, large station edits, double slip switches, line waypoints
  - NEW: lobby in the main menu. "Open the lobby" opens the host's session without loading the game: the players join it
    and see who is there, then the host clicks "Start the game", every player receives the host's savegame and every
    game loads it at the same time; the session starts once they are all ready (before, the host's game loaded at once
    and each player who joined reloaded every game). Joining a game already running works as before. A lobby closed by
    its host tells its players.
  - FIX (issue #27): a waypoint added to a line vanished after about a second, and every line change in a session
    removed the line's waypoints. The line was rebuilt without them (they were taken for engine data); their track
    travelled as a raw entity id. The waypoints are now rebuilt, their track travels as a reference (a waypoint whose
    track is not found is dropped alone, one on a track that runs the other way round takes the opposite place), and the
    state check compares them.
  - FIX (issue #28): a track build that moved one signal and re-created another was refused on the other games
    ("Collision") and reloaded every game. The rebuilt native street proposal now removes the signals the tool removed,
    and places the re-created ones on the new segments afterwards.
  - FIX (issue #29): after the host restarted MPFever, a player who joined again from the main menu received the host's
    game but never loaded it: the load number repeated (the host's counter starts again at 1) and the game took it as
    already loaded. The number is now unique.
  - FIX (issue #30): a whole number above 2,147,483,647 (a company balance, for example) could not be written in a
    message nor hashed ("%d" is 32 bits in the game's Lua). Strings are now escaped by a fixed list of control bytes
    instead of the locale-dependent %c, which could split a UTF-8 character.
  - FIX (issue #31): when the host does not answer, the connection error no longer lists the expected IPv6 failures of a
    PC without IPv6 first: they are folded into one note after the real reason.
  - FIX (issue #32): the state check held the simulation about 0.3 s every 10 s on large maps. Its expensive parts
    (construction parameters, roads, constructions and node configurations) now take turns, one group per check; the
    launcher keeps a difference per part until that part is checked again.
  - FIX (desync): a build the engine applies twice at the same moment (a double slip switch set next to another one) was
    taken by every game for a new build of its own player and shipped: each game then replayed the other's copy a few
    steps late, and a build applied a few steps late is enough to make the people, the towns and the vehicles drift
    apart (one of the reloads of our tests). A captured build identical to the action just applied at that moment is no
    longer shipped.
  - TESTS: the autotest's bus stop scenario now holds its build until its announced step like a player's tool build
    (sent at once, it was replayed late on the other game and the towns drifted after a few minutes).
  - DIAGNOSTICS: every game logs the cost and the town impact of each build ("build stats"), and keeps the game script
    states of its last 12 checks (sdump_ring_*.txt in the session folder): a drift of the towns can be traced to its
    first differing value.
  - FIX (issue #24): the game's speed buttons kept showing the speed this player chose last: the other player's changes
    were applied but not shown. The interface waited for an answer to its speed request that MPFever never gave, and
    stopped following the game's speed. The request is answered, and the buttons show the session's speed (not the
    engine's, which the lockstep holds at pause between steps).
  - FIX (issue #25): editing a large station made the other games very slow, for seconds per module. Each part of the
    station whose number differs on the other game was searched by reading every node or segment of the map, once per
    reference. The map is now indexed once per action and each part is looked up once: the same results, about 500 times
    fewer reads.
  - FIX (issue #26): a double slip switch set in the node window had no effect in a session. The replay dropped the node
    configuration, which is the whole build of that window. A build that only changes node configurations now keeps them.

0.3.7-experimental - crashes on bulldozed stations, signals in tunnels, line routes of the client
  - FIX (crash, issue #15): bulldozing a street station crashed the other player's game. The other game removed the
    station's entrance street but not the station, which stayed connected to a removed node. The station is now removed
    with it, as on the player's game.
  - FIX (issue #16): a rail signal placed on a track rebuilt the track on the other game as normal track at ground level
    (a tunnel was dug out, a bridge became a track on the ground) and without its distance: the games differed and the
    host's game was reloaded. The segment now keeps its kind, its distance and its decorations. A stop or signal the other
    game refuses now reloads the host's game at once instead of being only written in the log.
  - FIX (issue #17): a build made while the host's game is reloaded for everybody (after its save, before every game has
    loaded) was kept by the other games and lost by its builder. Such a build is now dropped everywhere, and the chat says
    so, so that it can be built again.
  - FIX (issue #18): after several reloads, the native module took the two states of the game for new games (its table of
    known states was full and always replaced the same entry), dropped a held build, and from then on released every build
    at once: the other games built them late. The table is now used in turn, and builds are released by their number
    instead of a count.
  - FIX (issue #19): several quick edits of one station (modules added one after the other) were replayed before the
    previous one was built, and refused. A replay now waits for the previous one.
  - FIX (issue #20): a bulldozer replayed on the other games used other settings than the bulldozer (terrain alignment,
    buildings gathered) and could cost money there. Builds now carry the settings of the tool that made them.
  - FIX (issue #21): copying vehicles froze the game about 1 s per vehicle part and wrote 11 crash dumps each: reading the
    colour of a part tried the functions of its type one by one, and every failed read made the game write a dump. The
    vectors and matrices are now read directly, and a member that cannot be read is never tried again.
  - FIX (issue #22): "Send To Line" in the line manager: the result now carries the vehicle and the line, so that the
    window's follow-up runs (the vehicle leaves the list).
  - FIX (separate companies): a client's own line routes were not drawn on the map (they flashed and vanished): the map's
    line viewers are made while the game loads, before MPFever knows the client's company, and kept the savegame's.
  - FIX: a road joined to a street with stops was not built on the other game (the stops it moves were taken for a stop
    build): it is now rebuilt with its stops.
  - FIX (session): a player joining right when a session started never got the host's game (the start of the session
    cancelled the reload made for the player). A speed asked during a reload is now ignored.
  - FIX (session): going back to the game's main menu ends the session, even without opening the MPFever window (a new
    game started from the menu ran in the old session).
  - The tutorial is not supported in multiplayer (its missions are validated on each game separately, and a unique
    building made by one player blocks the other's task): the chat now says so when such a game is hosted.
  - NEW (thanks to SlikerDev, #11): IPv6. The host also accepts players over IPv6 and Steam invitations carry its IPv6
    address: a host behind DS-Lite (no public IPv4) is reached when the joining player has IPv6 too. The chat reader of a
    client starts once it is connected.

0.3.6-experimental - fixes from the GitHub issues
  - FIX (issue #12, builds lost while paused, then a crash): while the game time stood still (a paused session, e.g. in the
    tutorial), every replayed action (vehicle purchase, line, name...) was counted as a build to come back, so the
    player's own builds were taken for replays and never sent to the other games. Only the actions that can make a build
    are counted now.
  - FIX (issue #12, crash): an action on a vehicle or a line whose purchase or creation had been skipped used the plain id,
    which was another entity on that game (the engine crashed on it). A vehicle or a line must now still be one.
  - FIX (issue #12): an action skipped on a game because something it refers to is missing (the games already differ)
    reloads the host's game at once, as a build that cannot be reproduced does. A skipped action of a paused session is
    now reported to the host too, and the games are checked during a pause when actions went through (once every game is
    at the same time and no action came for 5 seconds).
  - FIX (issue #13, rejoining from the main menu): "Cancel" in the MPFever window now ends the session (the next host game
    went to the in-game scripts, which do not run in the main menu: the game never loaded). Joining from the main menu
    ends what is left of an earlier session, a Steam invitation is no longer ignored there, and a reconnection of the
    earlier session can no longer connect a second time.
  - FIX (issue #14): editing an existing street station (adding a module to a modular terminal) was refused by the other
    games ("Collision" with the old station) and reloaded everybody: the old station is now replaced as on the player's
    game, and its stations kept (the lines stopping there keep their stops).
  - FIX (issue #4): the session starts when the games loaded the same savegame but one ran a few steps more (up to 10).
  - Build: the native module links with recent Visual Studio toolsets (__chkstk, issue #4 and PR #8).

0.3.5-experimental - terrain edits in step, in-game chat
  - FIX (crash): a client crashed when the host built a road across a street where the client had put bus stops. Two causes:
    the stops were rebuilt on the other games without the junction settings the stop tool puts back (lane connections,
    crosswalks), so the junctions differed; and a road that cuts a street carrying stops was rebuilt in a way that left the
    stops on the removed piece of street (the game then crashed computing their catchment area). Stops are now rebuilt with
    their junction settings (checked on the savegame of the report: the same junctions as on the player's game), and a build

    Checked with the road of the report: rebuilt on the other game with the same pieces of street, the stops kept. If the
    other game still cannot reproduce such a build, the host's game is reloaded for everybody instead of a crash.
  - FIX (session): the first click on "Host" ended the session at once (the client could never join, the host had to click
    again), and after that the multiplayer window no longer closed by itself. The window now ends a session only when it is
    opened from the main menu after leaving a game.
  - KNOWN ISSUE (separate companies): on the other players' games, the routes of their own lines are not drawn on the map
    (they flash and vanish). The lines themselves work. A first attempt (the map's line viewer reads the player's company)
    did not fix it; the search goes on.
  - FIX (crash, desync): a terrain edit (raise, lower, flatten...) cannot be held like the other builds, so it is made at
    once on the game of the player who makes it; a game already a little further in time made it a few steps late. An edit
    changes the reputation of the nearest town, so the towns then drifted apart, and a client crashed when the host
    demolished a station afterwards (the engine still found something of the client's own town connected to it). Now, while
    a player has a terrain tool in hand, the other games stay a little behind that player's game and make every edit at
    exactly its time. Checked: 12 edits in a row by the host and by the client at x4, all at the same step, no difference.
  - FIX (desync): an action arriving close to a moment where a game had to wait for the other players could still be
    applied one step late at x4 (the game ran on at speed, or asked the engine for its exact steps while it was still
    running). Exact steps are now used whenever an action is near, and only once the simulation really stopped.
  - FIX (separate companies): a terrain edit was paid on the other games by THEIR player's company (corrected afterwards by
    the host's money check): it is now paid by the company of the player who made it, as on that player's game.
  - The state check no longer reports a terrain difference while an edit is still on its way to the other games.
  - A difference in the simulation (towns, vehicles, passengers...) now reloads the host's game after 30 seconds instead of
    5 minutes: the games no longer drift by themselves since 0.3.4, so such a difference comes from an action applied
    differently, and playing on with other towns can crash a game.
  - NEW (thanks to SlikerDev): chat in the game. A "Chat" card in the pause menu (and a button in the MPFever window) opens
    the chat window; new messages show for a few seconds at the left of the screen; players who join get the last 50
    messages. Messages go through MPFever.exe, never through the simulation.

0.3.4-experimental - no more crash on resynchronisation, companies stay in sync, shared stations usable
  - FIX (desync, the main cause): the game's Lua (5.2.2) seeds the hash of its strings with the clock and memory
    addresses, differently on every PC: the game's own scripts (towns, industries, the scripts of the constructions)
    walked their tables in a different order on each game and took different decisions - towns grew differently, a
    new industry got its lanes numbered differently, then people, cars, pollution and money drifted apart. The native
    module now gives Lua the same seed on every game. Checked on the savegame of a report: two games left alone stay
    identical for 18 minutes of game time (three runs, every entity created and removed in the same order; before:
    apart after 6 minutes), a 10-minute session at x4 stays identical, and so do the scenarios with players' actions.
  - NEW (thanks to SlikerDev): an MPFever window in the game, opened from a card in the pause menu: the players and
    their link (connected, behind, not responding, loading, left), the sync state and, for the host, Steam invites.
    It stays open while playing and can be moved or closed. The station window offers a list of fees (not shared,
    $100 ... $50,000 per stop) instead of the - / + buttons, and follows a change at once.
  - NEW (for developers): docs/RESEARCH.md - what we learned about the engine, the causes of desyncs and what must
    be synchronised in co-op and with separate companies.
  - NEW (diagnostic, for developers): a full census of the game state (every component of every entity) compared
    between two games (MPFEVER_CENSUS with the "det" autotest, or the "census" scenario).
  - FIX (crash): the host's game (or a client's) could crash while loading the game of a resynchronisation, or a little
    after it: the module still wrote this machine's company into the game that had just been unloaded (freed memory).
    It is now written by the simulation only, into the game it is running. Reproduced on the savegame of the report
    (crash at the second resynchronisation) and checked: three resynchronisations in a row, no crash.
  - FIX (crash): a building held when a resynchronisation started (its tool clicked just before) was released into the
    newly loaded game and crashed it; such builds are now dropped.
  - FIX (desync, separate companies): the games of the players drifted apart within a minute (vehicles, money of the
    savegame's company, then towns) and were resynchronised again and again: four readings of the engine's "local player"
    on the simulation thread made a game playing another company simulate differently. They now give every game the
    same company, while the interface, its tools and windows act as the player's own company (money checks before
    building, Finances window, line tool, vehicle assignment). Checked on the savegame of the report: identical for 5
    minutes with a resynchronisation in between (before: a drift after 30 seconds).
  - FIX (desync): a depot or station built at the dead end of a street (its entrance joining the street's last node)
    could not be rebuilt on the other games ("removal differs", then a resynchronisation): fixed and checked on the
    savegame of the report (roads identical to the player's).
  - FIX (shared stations): the line tool did not let another company pick a shared station; it does now (only the
    stations shared with a fee above 0), stops by the street included. Checked: a client's line through the host's shared
    stations runs, its vehicles stop there and pay the fee.
  - FIX (session): going back to the game's main menu left the session running (a new game needed the game to be
    restarted). Opening the MPFever window of the main menu now ends the left session; host or join again from there.
  - FIX (separate companies): the money popups over the buildings only show the player's own company.
  - FIX (separate companies): a player could not build when the HOST's company was out of money (and could when their
    own was): the construction tools checked the money of the savegame's company. They now check the player's own
    company, and the tools are made for the player's company (map icons, line tool, stations of the player's own).
  - FIX (desync): a vehicle bought by a player could be bought twice or three times on the host's game (a copy stayed
    in the depot) and the next actions of that player were lost: an action is now applied once, whatever happens to
    the queue meanwhile.
  - NEW (separate companies): every station or stop a player builds is shared with the other companies from the start,

0.2.10-experimental - terrain edits are copied, no more reload
  - Raising / lowering / levelling the ground is now copied to the other players like any other
    construction, by both the host and the clients. Before, a terrain edit made the host reload
    its game for everybody (a resynchronisation that takes time) and a client's edit stayed local.
    How: a script cannot read or write the cells of a terrain edit, so the native module copies
    them when the engine applies the edit (the cells are packed; at worst about 11 bytes of text per cell),
    the mod ships them with the game time, and on the other games the module copies them into an
    empty ground edit of the same size as it enters the engine's command list. The edit is made at
    once on the game of the player who edits (the terrain tool cannot be held like the others)
    and at the same game time on the others when they have not passed it yet, otherwise a step
    later (logged as LATE). The cells are first handed to the native module, which confirms, and only
    then is the empty ground edit sent, so a failure can never flatten the ground. Tested on two games: a 12x12 and a 300x300 cells patch with uneven
    heights, both directions, speed 1 and 4, paused game: same ground afterwards (sum of the
    heights of the patch identical), no desync.
  - New check in the state comparison: "terrain" (the sum of the checksums of the edits applied).
    A lost or doubled edit shows in the next check and reloads the host's game.
  - If the native module cannot copy an edit (unknown game build, unreadable cells) the old
    behaviour remains: the host's game is reloaded for everybody. A terrain edit that comes with
    other construction work, ground paint and the trees brush are still not copied (logged); neither is an
    edit of more than about 3 million cells (the host's game is reloaded then).
  - The command audit now also separates the commands of the simulation loop from the others on
    build 40420 (the address was only known for 40408).
  - Diagnostics for the next tests: native.log now says, once per tool, with which options the game's
    construction tools build ("build context from ...": terrain alignment, street graph cleanup,
    gathering of buildings...). It is meant to find out why a road built from an existing junction can leave
    a slightly different lane-connection setup on the other games ("nodeConfigs" in the state check).

0.1.1-experimental - synchronisation fixes
  - Random numbers of the game mechanics (loan offers, contracts, events) are now
    identical in every game: no more divergence of loans after a few minutes.
  - False alarms removed from the state comparison (internal engine counters), which
    caused needless resynchronisations at the start of a session.
  - No more speed request loop after a resynchronisation.
  - Notification sounds are no longer played twice.
  - Constructions from a previous session are no longer sent again at startup.
  - Lines: stops can be added in the line editor again (results of an earlier
    session no longer hide the new ones); lines and every other action now work
    while the game is paused, on every player's side.
  - Removing a stop with the bulldozer is replicated (the stop used to stay on the
    other players' maps).
  - Fewer interruptions: a slight drift of the engine's own simulation (vehicle
    positions, passengers, town statistics) is reloaded only if it lasts 5 minutes;
    real differences (roads, stops, lines, buildings, finances) still trigger an
    immediate resynchronisation.
  - Root cause of the slow drift found and fixed: on processors with 8 threads or
    more, the engine updates the game scripts (towns, loans, industries...) in
    parallel, in an order that depends on thread timing. The native module now gives
    them their own pool with one worker, as the engine itself does on smaller
    processors. Only the scripts' update is affected: the simulation, the rendering
    and the loading keep every core. Result in testing: 7 minutes at x4 without a
    single difference, and the same speed as before.
  - Actions applied a few steps late on another player's game at x4 (a game could
    pass its stop point while the interface reacted): actions are now stamped with
    a reserve for it, and games stop exactly at their stop points (exact steps).
    This was the cause of vehicles drifting after purchases and line changes.
  - Fewer synchronised slowdowns: wider waiting window between games.
  - Road upgrades that move a town building: the building stays a town building on
    the other players' games (it used to become the player's construction).
  - The game's speed request at startup no longer floods the launcher log.
